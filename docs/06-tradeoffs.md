# 06 · 技术取舍：我们故意不做什么

教学仓库的价值一半在"做了什么"，另一半在"**故意不做什么，以及为什么**"。
本文逐条记录取舍，避免读者误以为这是漏做。

## 取舍 1：不做多进程租约（no leader lease / fencing token）

- **文章/生产版可能有**：多实例部署时用租约 + fencing token 防止脑裂，
  旧 leader 恢复后被新 leader 用更高 epoch 顶掉。
- **本仓库**：单机单实例，pid 文件 + 单一恢复启动器。
- **为什么**：租约要引入时钟、网络分区、租约续期失败检测，教学焦点会从
  "事务边界与崩溃窗口"漂移到"分布式共识"。单实例已经能演示 90% 的
  恢复语义；租约是另一门课。
- **代价**：不承诺并发 stale 接管（见 `09`）。

## 取舍 2：不做事件溯源（no event sourcing）

- **文章/生产版可能有**：所有状态变更存为不可变事件流，状态由重放事件
  重建。
- **本仓库**：SQLite 直接存当前状态 + outbox 表；恢复 = 读当前状态 +
  重发 outbox。
- **为什么**：事件溯源要解决事件 schema 演进、快照压缩、重放副作用过滤，
  对教学来说是额外一层。用"状态 + outbox"已经能讲清 T1/T2 窗口。
- **代价**：没有完整审计轨迹；`workdir/` 只是可重建产物，不充当事件日志。

## 取舍 3：不承诺端到端 exactly-once

- **直觉诱惑**："都 messageId 去重了，就是 exactly-once 吧？"
- **本仓库立场**：**只承诺 at-least-once 投递 + 幂等消费**。
  `channel.db` 去重只能压住"本库见过的 messageId"，压不住外部副作用
  已发生但 ack 丢失的窗口。
- **为什么**：把 exactly-once 当卖点会误导下游作者把副作用写成非幂等。
  见 `07-exactly-once-counterexamples.md`。

## 取舍 4：模型与通道全部 mock

- **为什么**：教学必须确定性。真实模型延迟不确定、真实通道有网络抖动，
  无法稳定注入"T1 已提交 T2 未提交"这样的精确崩溃点。
- **代价**：性能、并发压力、真实错误码形态未覆盖。

## 取舍 5：依赖为零（Node 内置）

- 用 `node:sqlite`、`node --test`、标准库，零 npm 运行时依赖。
- **代价**：`node:sqlite` 是实验特性，启动有 `ExperimentalWarning`——
  教学原型接受该警告（见 `09`）；真实生产应换 better-sqlite3 或迁移。

## 取舍 6：doctor 只读、不自动修复

- `doctor` 发现 schema 未知 / pid 异常时**只报告、不动手**。
- **为什么**：教学现场要让你亲手看到"坏状态长什么样"；自动修复会把
  学习点（崩溃窗口、悬挂 snapshot）静默抹掉。
